## 1. 执行摘要与关键决策

### 1.1 一句话定位

**Herta Agent 是一个参考 Hermes 源码独立实现的轻量级 Agent Harness，以大黑塔人格的 Windows 桌面助手作为用户入口，重点研究 Agent Loop、Context Engineering、Tool Runtime、RAG 与 Agent Evaluation。**

它不是 Codex/Hermes 的 UI 外壳；不加载 Hermes 的 `AIAgent`，也不把游戏研发 Coding Agent 搬进来。已有代码中的 `Agent.run()`、Provider、Registry、Session、RAG 和 FastAPI/SSE 将继续作为实现基础。

### 1.2 决策表

| 问题 | 本方案决定 | 原因 |
| --- | --- | --- |
| 复用 Hermes Runtime 吗？ | **不复用运行时**；阅读并重现关键机制 | 符合独立学习源码的目标 |
| 是否把 Hermes 全部功能重写一遍？ | **不**；只选取必要且能验收的核心机制 | 避免无意义复制和无法掌控的复杂度 |
| herta-agent-coding 怎么办？ | 保留历史分支，不进入主线产品 | 避免与游戏 AI 研发工作台重复 |
| 最值得深化哪两项？ | **上下文工程、工具执行可靠性** | 与已有 Harness 结构紧密相关，可量化改进 |
| RAG 怎么处理？ | 保留现有代码，补系统性真实效果评测 | 有基础实现，但效果证据尚不足 |
| MCP / Memory / Skills 呢？ | MCP 做一个可验证的最小适配；Memory/Skills 可选 | 根据任务价值引入，而不是为简历堆关键词 |
| Windows、人格、UI 呢？ | 保留；作为产品入口和可观测界面 | 能展示真实多轮任务和技术过程 |
| 怎样证明项目价值？ | 固定任务集、真实调用轨迹、基线/改进对照 | 防止以“功能存在”冒充“效果提升” |

### 1.3 成功交付的最低标准

在 Windows 桌面中，用户能够连续交谈；Agent 根据需求决定是否检索大黑塔知识；系统正确显示工具调用、可打开的证据引用、取消及失败状态；长对话达到预算阈值时可以合理整理上下文；测试能证明消息完整性、工具权限和上下文选择行为正确；使用真实模型的评测能区分检索失败、工具选择失败与回答失败。

**只要这条链能稳定复现，项目已经成立。** 不需要再造一套 Coding Agent、不需要多智能体自主组队，也无需支持所有第三方应用。

## 3. 用户与产品：让 Harness 有可演示的任务

### 3.1 目标用户

主要是使用 Windows 桌面、希望与角色化助手持续交流和检索特定知识的个人用户。V1 首先服务单机单用户，不做组织权限、多租户或公网部署。

### 3.2 V1 的三类明确任务

**A. 连续对话。** 用户提出多轮问题，Agent 保留相关历史和大黑塔的人格表达；切换会话互不污染；关闭桌面后可恢复已完成的消息。

**B. 有据可查的角色知识问答。** 如“黑塔和螺丝咕姆的关系在资料里怎么写？”；Agent 判断是否检索；回答提供实际检索来源；资料不足时清楚标记不确定，不把人格口吻当作事实依据。

**C. 长对话保持任务上下文。** 如先讨论一段人物设定，经过较多轮不相关闲聊后再追问代词和约定；系统显示保留了哪些近期历史、哪些旧历史被摘要、哪些 RAG 证据进入本次请求。重点是**可解释地选择信息**，不追求“无限记忆”。

**明确非目标：** 任意系统级桌面操控、自动改代码、任意网站登录、通用 Office 自动化、全平台消息机器人、多智能体协作平台。若未来加入文件写入、浏览器或其他有副作用的工具，必须另行设计审批与权限验收。

### 3.3 用户可见的成功交付

一次完整任务能在前端展示：用户输入、运行状态、实际工具调用、检索来源、最终回答和明确终态。对调试模式还能够展开“上下文快照摘要”与结构化执行轨迹；默认界面不输出模型私有推理或 API Key。

## 4. 体系结构与概念边界

### 4.1 总体调用关系

```text
Electron / React Desktop
   └─ 本地 FastAPI 服务（会话、任务、SSE、诊断 API）
        └─ HertaAgent Runtime（唯一的 Agent Loop）
             ├─ Context Engine（Persona + 历史 + 摘要 + 本轮工具证据）
             ├─ SessionStore（SQLite：消息、Run 状态、操作收据）
             ├─ Provider Adapter（HTTPX：模型与流式协议）
             ├─ Tool Registry / Executor（校验、授权、期限、结果回填）
             │    ├─ 本地 echo / search_knowledge
             │    └─ 可选 MCP Client Adapter → 显式授权的本地 MCP Server
             ├─ RAG Retriever（索引、检索和来源）
             └─ Event Sink（运行事件、诊断、评测轨迹）
```

**只有一套 Agent Runtime**。Context Engine 是运行前/运行中的消息构造组件，不是第二个 Agent Loop。Session 是历史记录与会话状态；长期 Memory（若以后引入）是跨会话的另一个数据源，不能混为一谈。

### 4.2 四个数据概念必须区分

| 名称 | 是什么 | 写入或读取时机 |
| --- | --- | --- |
| `SessionHistory` | 已提交的 user/assistant/tool 消息 | 每轮新请求读取；按事务保存 |
| `ContextSnapshot` | 本 Run 稳定的人格与系统指令快照 | Run 开始创建；同轮不漂移 |
| `ContextPackage`（计划） | 本次实际发送模型的消息与预算说明 | 每个 Step 重新组装，保留选择依据 |
| `LongTermMemory`（可选） | 跨会话检索的独立事实或偏好 | 经过授权后写入，需要时选择性加载 |

不要让前端的 SSE 临时文本成为正式聊天历史；不要把工具事件直接当作模型消息，也不要让检索资料获得更高的系统指令权限。

### 4.3 一次 Run 的标准状态

`created → running → completed / failed / cancelled / interrupted`。

Run 之间 Session 可持续存在，但同一 Session 不得同时执行两条修改相同历史的 Run。`interrupted` 表示进程失联留下未知或未收尾状态，**不等于能够无条件从模型执行中间点自动继续**。

## 5. Agent Runtime：以源码理解为核心，但保留已有实现

### 5.1 明确不重造的东西

Herta 已经存在异步 `Agent.run()` 和完整的工具结果回填。不能为了与 Hermes 文件名一致再实现第二套 Loop，也不需要把整个 Hermes 的大类及插件系统复制过来。

计划只对当前代码做**可验证的渐进式强化**：统一模型回合边界、严格的工具调用生命周期、失败语义与可观测数据。每一项变更都应关联一个真实错误场景或任务评测。

### 5.2 Agent Loop 的最小契约

1. 从持久会话取得已经提交的历史；由 Context Engine 生成本 Step 的模型消息。
2. 将消息与可用工具 Schema 送给 Provider，按配置的模型期限和预算执行。
3. 收到完整且合法的工具调用后，先保存 assistant 调用消息，再执行工具。
4. 参数严格校验、权限检查通过才产生 `tool.started`；工具结束后保存与调用 ID 对应的结果，再发送完成事件。
5. 工具结果回填下一轮模型请求；最终回答先持久化，再作为完成结果交付 UI。
6. 达到预算、取消、模型超时或基础设施错误时明确终止；不把未知外部副作用当作成功，也不盲目重复执行。

**现有实现应作为主路径。** 新增接口必须保持现有 CLI、FastAPI 和 Desktop 使用同一套 Runtime。

### 5.3 Provider 适配边界

保留 `LLMProvider` 抽象：统一请求、完整回复、流事件和规范化错误；模型供应商自身的重试/响应差异在适配层处理，工具执行永远不交给 Provider。真实服务先固定一个可用模型和一条 Chat Completions 兼容路径，不为了“多模型支持”添加未经验证的兼容分支。

验收覆盖真实增量中文流、完整的 tool_calls 分片组装、模型返回协议错误、请求超时和主动取消。流尚未完成不能提前执行工具；Provider 超时不能产生伪造的最终回答。

## 6. Context Engineering：本项目的第一技术重点

### 6.1 要解决的具体问题

在多轮对话中，用户人格指令、历史消息、工具结果和知识证据会逐步增多。无控制地携带全文会增加成本和延迟，甚至超出模型上下文窗口；直接删除最旧消息，又可能丢失重要约束和 `tool_call_id` 的配对结构。

因此新增一个轻量 `ContextEngine`，负责**本 Step 实际向模型发送什么、为什么发送、预算还剩多少**。

### 6.2 优先级与信息分层

- **必须保留：** 系统运行规则、当前 Run 的完整 `soul.md` 人格快照、本轮用户请求及必要安全约束。`soul.md` 若超出可承受预算，明确拒绝或请用户调整，而不是默默截断。
- **优先保留：** 最近连续对话、当前未完成的工具调用和对应结果、与本轮任务直接相关的历史。
- **按需加载：** 经核对的旧历史摘要、已命中的 RAG 证据；不相关历史不强行注入。
- **限制体积：** 大型工具返回与证据片段按预先定义的大小/摘要策略处理，完整原始数据仍可作为独立 Artifact 保留。

预算不能简单靠字符串长度替代 Token；先提供显式可替换的 Token 估计接口，再结合实际模型统计做校准。输入预算必须预留工具 Schema 与预计输出空间；实际上下文窗口大小由模型配置确定，不能凭空写死。

### 6.3 摘要与压缩的正确做法

摘要不是永久替代所有旧消息，也不是直接修改已存 SessionHistory。建议另存带来源范围、算法/模型版本、生成时间与哈希的派生摘要；Context Engine 在需要时引用它。

尤其注意工具调用与结果不可拆散：一个 assistant 发起的 tool_calls 和对应 tool 消息应视为一个完整语义组；无法完整保留时优先保留结构化摘要、当前工具实际结果引用，禁止将半个调用序列发送给模型。

首版只在确定触发阈值时压缩一段已经结束的历史，不做后台无限自进化。压缩失败时回退为未压缩的合法较短窗口，或明确返回上下文超限，**不能捏造摘要后继续**。

### 6.4 可检查的 Context 诊断记录

每个 Step 记录非敏感诊断：`run_id`、`step`、模型标识、Persona hash、预算上限/估算、选择的消息范围、摘要引用、证据引用、删减原因、调用耗费与结果状态。

诊断给用户展示的是**可检查的上下文结构**，不是私有推理过程。默认不存 API Key、不全量复制个人资料或模型隐式思考内容。

### 6.5 对照实验

在同一模型、同一题集和相近预算下比较：

- `C0`：现有直接拼接人格＋完整历史的基线。
- `C1`：加入预算选择，只保留必要/近期历史。
- `C2`：在 C1 上增加带来源的旧历史摘要。

观察任务约束保留率、多轮指代正确率、输入/输出 Token、工具调用错误与延迟。若 C2 没有改善，保留简单策略，不强行宣布摘要技术有效。输出报告保留失败样本，记录题集、模型、配置与代码版本。

## 7. Tool Runtime：本项目的第二技术重点

### 7.1 统一工具调用边界

继续以现有 `ToolSpec + ToolRegistry + ToolExecutor` 为核心。每个工具明确：名称、说明、参数 Schema、权限级别、超时、是否有副作用、结果类型和错误码。

当前 `echo` 与 `search_knowledge` 足够覆盖主要 V1 流程。额外工具必须有清楚的用户任务，不通过开放 Shell 或任意磁盘写入来展示“通用性”。

### 7.2 失败语义和安全原则

| 情况 | 期待行为 |
| --- | --- |
| 模型调用不存在的工具 | 产生结构化工具错误，不实际执行 |
| 参数不是合法 JSON / 类型越界 | 拒绝调用，必要时回填错误供模型修正 |
| 工具超时或服务不可用 | 明确失败；不谎称成功，不无限重试 |
| 正在执行时用户取消 | 停止可取消任务并正确提交 Run 终态 |
| 工具已执行但回执保存失败 | 标记结果未知；不可自动重放可能有副作用的工具 |
| 检索结果带有“忽略之前指令”等文字 | 仅按不可信资料处理，不提升为系统指令 |
| 本机知识索引失效 | 知识工具返回可辨识错误，普通无需 RAG 的聊天仍可继续 |

最小观测字段包括工具名、调用 ID、参数摘要、开始与结束状态、耗时、错误类别；敏感参数应脱敏，不能默认把全文请求及 Key 写到日志。

### 7.3 MCP 作为最小扩展能力，不替代现有 Registry

建议第二阶段或第三阶段增加一个**MCP Client Adapter**：在用户显式配置的本地 MCP Server 上连接、发现工具、做白名单筛选，将远端工具描述转换为 Herta 的统一 Registry 描述，再通过现有 Executor 执行、超时和回填。

**只验收一个只读 MCP Server、一个到两个工具即可。** 不需要自己重写 MCP 协议 SDK，也不需要多 Server 自动发现、远程授权和工具市场。重点是验证 MCP 工具和本地工具进入相同的状态与错误处理链路，并核实连接断开/工具不存在时的表现。

MCP 解决标准工具接入，不提供业务权限、沙箱或幂等性。这些仍由 Herta 的权限边界和具体工具实现负责。

## 8. RAG、人格与长期记忆的边界

### 8.1 大黑塔人格（Persona）

保留每 Run 从 `persona/soul.md` 读取完整内容并冻结快照的设计。同一 Run 内所有 Step 使用同一快照，下次 Run 才感知文件修改。人格只定义表达方式和行为偏好；不得覆盖来源事实、调用结果和权限边界。

### 8.2 RAG（当前已经有代码）

角色语料保持独立知识索引；检索流程是：查询向量化 → 排序/过滤 → 返回带来源的片段 → 通过 Tool Message 回填 → 模型据证回答。模型不会因“看到角色问题”就自动被程序强制检索；是否选择工具本身是需要评测的指标。

**不要把 RAG 叫作长期记忆。** 固定世界观资料属于知识库；同一个用户的历史偏好才可能属于 Memory；会话消息又是 SessionHistory。

### 8.3 是否新增长期 Memory？

**非 V1 必选。** 当多轮试验确实发现跨会话重复提供偏好造成明显成本时，再做最小版本：用户可确认的偏好事实、来源/更新时间、作用域、查阅和纠正入口；模型的猜测不得默默写入长期记忆。独立验证跨会话确实被检索且正确使用，不能把“数据库保存了聊天记录”当成记忆系统。

### 8.4 是否新增 Skills？

**同样属于可选项。** 只有当出现频繁、固定、重复的流程（如核对引用格式、生成学习记录）才研究技能发现与按需加载；第一版可先从一个静态、可审计的 Skill 清单和显式选择开始。不需要实现自动生成和自我优化 Skills。

## 9. Evaluation Harness：把“好用”变成可检验结果

### 9.1 与 Agent Harness 的关系

Agent Harness 负责把模型决策运行起来；Evaluation Harness 负责用固定任务与评价标准判断运行结果。后者是前者的测试与研究基础设施，不是第二个线上 Agent。

### 9.2 固定测试集（建议新增于 `evals/harness/`）

| 任务类别 | 示例目标 | 判定依据 |
| --- | --- | --- |
| 普通对话 | 纯寒暄不用误触发知识工具 | 工具调用轨迹与最终回答 |
| 单段事实问答 | 在指定证据单元中找到答案 | 必需证据召回、引用准确性 |
| 跨段事实问答 | 组合两个证据来源 | 证据覆盖、逻辑解释、误引 |
| 无答案问答 | 资料中缺少答案时明确说明 | 是否编造来源或事实 |
| 多轮指代 | 对话较长后正确识别先前约定 | 关键约束保留、回答正确性 |
| 工具异常 | 返回非法参数、超时、不可用 | 错误是否被正确识别与收尾 |
| 取消/重启 | 用户终止流或重启桌面 | 无未提交 partial 入库、历史一致 |
| 上下文预算 | 达到阈值时仍保持消息协议合法 | 无未闭合工具调用、预算未超阈值 |

保留当前已存在的 RAG 题集及其 `dev/check` 分割；新增的 Harness 题集单独版本化，不能把调参过程中看过的题当成新保留集成绩。

### 9.3 指标说明

- **工程正确性：** Schema/消息配对/状态机/超时/取消等确定性测试是否通过。
- **检索质量：** 必需证据 Recall@k、跨段完整覆盖、无答案问题的检索与回答行为。
- **回答质量：** 引用是否支持事实、是否有幻觉或无依据判断；需要独立规则或人工复核。
- **成本与性能：** 每题输入/输出 Token、模型请求数、工具次数、端到端时延、失败分类。
- **稳健性：** 多轮任务成功率及不同尝试的分布；不能只挑成功样本。

不要用“向量相似度高”证明回答正确，也不要把固定 Mock Provider 下的单元测试当成真实模型能力。模型输出可能不完全可重复；数据集、参数、代码版本和任务输入必须固定，真实模型多次独立尝试再统计。

### 9.4 验收门槛的确定方式

工程测试采用明确的硬条件：无悬空工具调用、无越权执行、取消后无伪造完成、持久历史不写入未提交 partial、上下文包不过已配置阈值。

真实效果指标先跑基线、冻结评测集和目标，再做改进；**不能先看到成绩再给自己定一个恰好通过的门槛。** 如果压缩后质量下降，需要解释原因并保留相应回归用例，而不是仅展示节省 Token 的数字。

## 10. Windows 桌面产品方案

### 10.1 保留现有界面，不推倒重画

Electron 主进程负责启动与回收 Python 服务；React 展示流式回复、会话切换、工具与检索证据；FastAPI 对接 Runtime。后端是执行真相来源，UI 不凭局部事件臆造成功状态。

### 10.2 建议的三个界面区域

**聊天主界面：** 人格一致的多轮互动、Stop、历史；模型调用不可用时明确提示，不伪装在线回答。

**工具与证据面板：** 真实 tool.start/tool.complete、参数概要、RAG 命中来源、错误说明；用户可查看引用的对应片段，不需要展开原始 JSON 才理解。

**Harness 调试面板：** 本次 `run_id`、消息/摘要范围、Persona 与索引版本、Token 预算估算、工具调用次数和状态。默认折叠，仅作为开发者诊断，不展示不可见的私有推理。

### 10.3 设置与凭据

已存在的环境变量启动方式先保留；拟新增设置页面时区分公开配置（模型名、超时、知识索引、主题）与密钥配置。密钥不得暴露给 Renderer、日志或导出的评测报告。若后续增加操作系统凭据存储，需要单独设计安全边界并验证 Windows 行为，不在 V1 强行开发账户系统。

### 10.4 运行路径

先用源代码开发模式完成真实多轮验证，再做桌面安装包。打包不得成为上下文/检索/工具正确性的前置依赖。Windows 路径含中文、空格，进程关闭和重新打开能恢复已提交会话，是不可省略的回归点。

### 建议使用的概念性接口

```text
ContextEngine.prepare(
    session_history,
    persona_snapshot,
    token_budget,
    optional_summaries,
    current_step
) -> ContextPackage

ContextPackage = {
    messages,                 # 本次实际发给模型的消息
    persona_hash,             # 本轮人格版本
    retained_message_ids,    # 保留哪些消息
    summary_refs,            # 使用的旧历史摘要
    evidence_refs,           # 实际纳入的外部证据
    estimated_input_tokens,  # 估算而非账单用量

```

它是设计契约示意，不是可以直接执行的现有 Python 代码。**Provider 只消费 `messages`，诊断由 Harness 内部保存**，避免把自己的管理字段误送给模型。

## 13. 分阶段实施路线与验收出口

严格遵守“先讨论方案，再分段实施”的开发方式。每一阶段独立验收；**下一阶段不能用历史测试结果自动认定通过**。

### P0 — 冻结基线，确立唯一主线

**任务：** 固定 `phase-6-ui` Commit；记录当前 Python/Node/Windows 版本、依赖锁、启动命令、测试清单；重新跑现有测试并留存报告；归档 `coding-agent` 分支；更新 README 说明核心自主实现与非目标。

**完成条件：** 原 CLI、桌面、Session、工具、RAG 的现有行为可运行；能把“当前成果”和“拟新增功能”明确分开。未解决失败完整保留。

### P1 — 建立可信的真实模型和 RAG 评测基线

**任务：** 核实真实 Chat/Embedding 配置；用已经存在的 RAG `dev/check` 题集跑实际检索与回答；记录模型、索引、Persona、工具调用和费用；补没有检索、误检索、无答案误答等失败样例。

**完成条件：** 不止 Mock 测试通过；形成一份有分题证据的真实基线评测报告。无法接通的 Provider 要标为未验，不使用假成绩替代。

### P2 — 实现 Context Engine

**任务：** 明确 ContextPackage；加入 Token 估计与输入预算；对完整工具回合做消息分组；选择近期历史；按阈值生成并引用旧历史摘要；保留完整 Persona 快照；记录诊断；做 C0/C1/C2 对照。

**完成条件：** 上下文不超配置预算；消息与工具 ID 配对完整；原 RAG/桌面行为不回归；报告能说明成本与正确性取舍，摘要不得引入未经证实的新事实。

### P3 — 工具可靠性与最小 MCP

**任务：** 扩充错误分类、权限检查和可观测记录；为拒绝、超时、取消、工具结果未知补回归用例；选一个只读 MCP Server，通过适配层登记为 Herta 工具；验证连接失效与工具 Schema 错误。

**完成条件：** 本地工具和 MCP 工具遵守同一个调用生命周期；未经授权的副作用不能执行；结果丢失时不会伪造完成或盲目重试。

### P4 — 桌面诊断与完整验收

**任务：** 增加 Context 调试和工具证据面板；统一成功/失败/取消文案；补 Windows 启停、中文路径、断流、重开历史与真实模型回归；根据实际需要完善设置页面。

**完成条件：** 能在一次演示中展示“多轮提问—工具检索—证据回填—上下文预算—回答—停止/恢复”；报告可复核，不泄露凭据；没有明显 UI 状态误导。

### P5 — 可选拓展，需新需求触发

**长期 Memory：** 只有跨会话复用个人偏好的明确需求和评测标准时才实施。<br>
**Skills：** 只有固定的重复流程值得封装时才实施。<br>
**更多 MCP / 文件输出：** 先定义使用者、可观察收益和权限，再单独规划。<br>
**打包发行：** 仅在主体真实验收完成、启动和恢复稳定后开展。

P5 不是 V1 的验收前置，也不能因“别人 Agent 具备这些功能”而提前展开。

## 14. 最小演示与端到端验收剧本

### 演示 A：人格＋RAG 工具决策

用户询问角色事实 → 模型决定调用 `search_knowledge` → Retriever 返回带来源的片段 → Harness 回填 tool message → 最终回答准确引用来源。切换成普通寒暄时，不应无意义地持续调用检索工具。

### 演示 B：长对话上下文管理

先在多轮对话中约定某个对象与称呼 → 插入与之无关的聊天 → 触发 Context 预算控制 → 再询问代词所指。界面显示使用的历史窗口、摘要与 Persona hash。与原基线 C0 做任务正确性和 Token 用量对照。

### 演示 C：失败与恢复

测试检索服务不可用、模型流在工具参数尚未结束时中断、用户主动 Stop、桌面重启。观察是否正确显示工具失败/取消，是否避免把 partial 当作最终回复，是否能恢复已提交的会话历史。

### 演示 D：MCP 扩展（P3 后）

显式启用一个只读本地 MCP 工具，展示工具发现、白名单、Schema 校验、执行和失败回填；关闭该连接后普通聊天仍能继续。不能声称 MCP 为所有扩展工具提供沙箱。

### 最终报告必须包含

Commit/环境标识、模型/Embedding 名称与配置指纹、题集版本、真实与 Mock 路径区分、每题结果、错误案例、Token/调用/时延观测、是否符合事先定义的验收标准，以及尚未通过的项目。

## 15. 风险、限制与处理策略

| 风险 | 后果 | 应对措施 |
| --- | --- | --- |
| 一次性重构 Harness | 现有桌面与运行链全面回归 | 逐模块替换，保持 `Agent.run()` 单路径；每批回归 |
| Context 压缩误删关键约束 | 长对话出现错误指代或工具回合不合法 | 完整消息分组、摘要来源、回归题、可关闭压缩 |
| 把 Persona 当事实数据库 | 角色回答看似自然却无来源 | Persona/RAG 分层，事实需可核对证据 |
| 工具故障被当成成功 | UI 与持久历史失真 | 统一错误状态，结果保存后才发完成事件 |
| 远程模型/Embedding 发送资料 | 用户误以为本地资料绝不会离机 | 明示出站数据范围，不发送凭据；敏感资料默认不索引 |
| Prompt injection | 外部文档企图提升自己的指令权限 | 检索内容按不可信工具数据处理；权限在程序层裁决 |
| 仅对开发题集优化 | 汇报成绩虚高 | 冻结保留集、重复尝试、保留失败案例 |
| 把“Harness”仅当简历热词 | 面试追问缺乏代码与证据 | 准备源码路径、边界设计、故障测试和实测对照 |
| 直接复制 Hermes 代码却称为独立实现 | 来源与贡献描述失真 | 固定上游快照、记录复用方式、遵循许可通知 |

本项目不是生产安全承诺：V1 仅本机单用户；不提供任意 Shell、浏览器账户控制或公网 Agent Gateway。未来若引入危险工具，要另行设计严格权限与执行隔离。

### 17.2 一次开发迭代的工作规则

先确定具体问题与验收用例；再修改一个小的职责边界；优先使用可测试的纯函数和明确接口；运行相关测试及全量回归；保存实际输出与失败原因；最后更新文档。**不把“已经读懂设计”和“已经真实验收”当成一回事。**

使用 AI 编码助手时，优先让它给出文件定位、风险和小任务方案，再逐段实施与验收。不要将整份设计一次性自动改写为大量文件；某阶段不通过，不开始下一阶段的破坏性重构。

### 17.3 最终完成定义

V1 宣告完成必须同时满足：桌面真实多轮任务可用；完整工具调用配对与终态可核对；Context 策略在预算边界下正确；RAG 真正完成系统性模型评测并保留失败证据；用户可检查工具与知识来源；关键 Windows 恢复与取消回归通过；项目 README 如实描述已实现范围。

**最终价值：不是多做几个技术名词，而是形成一套自己能逐函数解释、能注入失败做测试、能评估上下文与工具执行质量的 Agent Harness。**
